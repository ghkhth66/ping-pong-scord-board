2. 신뢰성 및 안정성 (Reliability & Stability) : 17점 / 20점
기준: 시스템이 오류 없이 안정적으로 작동하며, 장애 발생 시 복구할 수 있는가?
강점 (Pros):
atomic_write_json 함수를 구현하여 파일 저장 중 앱이 종료되어도 데이터가 손상(Corruption)되는 것을 방지한 점은 매우 전문적인 접근입니다.
load_room_state를 통해 모바일 환경에서 브라우저 새로고침 시 세션이 날아가는 Streamlit의 고질적인 문제를 훌륭하게 해결했습니다.
네트워크 오류(구글 시트 연동 실패 등)에 대비한 try-except 처리가 꼼꼼합니다.
감점 요인 (Cons):
상태 저장 및 접속자 관리를 로컬 JSON 파일(room_states.json, viewer_sessions.json)에 의존하고 있습니다. 만약 Streamlit Community Cloud나 Docker 컨테이너 환경에 배포할 경우, 인스턴스가 재시작되면 로컬 파일이 초기화되어 데이터가 유실될 위험이 있습니다.
3. 유지보수성 및 코드 품질 (Maintainability) : 14점 / 20점
기준: 코드를 읽기 쉽고, 수정 및 확장이 용이한가? (모듈화, 가독성)
강점 (Pros):
변수명이 직관적이며, 주석(특히 이모지를 활용한 시각적 구분)이 매우 훌륭하게 작성되어 있어 로직의 흐름을 파악하기 좋습니다.
config.py를 분리하여 상수와 CSS를 관리한 점이 좋습니다.
감점 요인 (Cons):
단일 파일 비대화 (Monolithic): 하나의 파일에 1,500줄 이상의 코드가 집중되어 있습니다. UI 렌더링 로직과 비즈니스 로직(전적 계산, 대진표 생성 등)이 강하게 결합(Coupling)되어 있어, 추후 기능 추가 시 스파게티 코드가 될 확률이 높습니다.
개선 제안: auth.py(인증), db_manager.py(구글시트/JSON 관리), league_logic.py(조편성 및 점수 계산), ui_components.py(화면 렌더링) 등으로 파일을 분할해야 합니다.
4. 보안성 (Security) : 13점 / 15점
기준: 정보와 데이터를 안전하게 보호하는가?
강점 (Pros):
st.secrets를 활용하여 민감한 정보(API 키, 마스터 비밀번호)를 하드코딩하지 않았습니다.
streamlit_cookies_manager에 암호화(Encrypted)를 적용하여 세션 하이재킹을 방지했습니다.
비밀번호를 평문으로 저장하지 않고 hashlib.sha256을 사용해 해싱 처리한 점이 우수합니다.
감점 요인 (Cons):
SHA-256은 단방향 암호화지만, Salt(소금치기) 가 적용되지 않아 레인보우 테이블 공격에 취약할 수 있습니다. 보안을 한 단계 높이려면 bcrypt 라이브러리나 hashlib.pbkdf2_hmac을 사용하는 것이 좋습니다.
5. 사용성 및 UI/UX (Usability) : 9점 / 10점
기준: 사용자가 이해하기 쉽고 조작하기 편리한가?
강점 (Pros):
Streamlit의 최신 기능인 @st.fragment를 적극 활용하여, 특정 버튼(출석체크, 제비뽑기 등) 클릭 시 화면 전체가 깜빡이는 현상(Full Rerun)을 방지해 UX를 크게 개선했습니다.
responsive_text 함수를 직접 구현하여 PC와 모바일 환경 모두에서 글자 크기가 깨지지 않도록 반응형 웹을 구현한 점이 탁월합니다.
st.toast와 st.balloons를 활용한 시각적 피드백이 훌륭합니다.
6. 효율성 및 성능 (Performance) : 8점 / 10점
기준: 자원을 효율적으로 사용하며 응답 속도가 빠른가?
강점 (Pros):
@st.cache_data를 적절히 사용하여 무거운 구글 시트 DB 로드 작업과 엑셀 파일 생성 작업의 속도를 최적화했습니다.
감점 요인 (Cons):
일반 사용자(Viewer)의 세션을 체크하기 위해 clean_and_get_viewers 함수가 실행될 때마다 JSON 파일을 읽고 씁니다(File I/O). 동시 접속자가 많아질 경우 디스크 I/O 병목 현상이 발생하여 앱 전체가 느려질 수 있습니다. (Redis나 메모리 기반 캐싱 도입 권장)

개발 및 코드 구현을 목적으로 Claude를 사용할 때 가장 효과적인 4가지 핵심 사용법을 정리해 드립니다.

1. 🏷️ XML 태그(< >)를 적극적으로 활용하세요
Claude는 다른 AI 모델들과 달리 XML 태그를 통해 문서의 구조를 파악하도록 특별히 훈련되어 있습니다. 앞서 우리가 만든 프롬프트의 마크다운(#) 방식을 XML 태그로 바꾸면 Claude의 이해도가 비약적으로 상승합니다.

Claude 맞춤형 프롬프트 구조 예시:
Copy
<role>
당신은 20년 차 시니어 Python/FastAPI 개발자입니다.
</role>

<task>
아래 명세를 바탕으로 완벽하게 동작하는 코드를 구현하세요.
</task>

<specifications>
1. 입력 데이터: ...
2. 핵심 동작 흐름: ...
</specifications>

<constraints>
1. 생략 없는 전체 코드를 작성할 것
2. 상세한 주석을 달 것
</constraints>
2. 💻 'Artifacts(아티팩트)' 기능을 반드시 켜세요
Claude 웹 인터페이스(claude.ai)의 좌측 하단 프로필 메뉴에서 'Feature Preview(기능 미리보기)'에 들어가 'Artifacts'를 활성화하세요.

효과: 코드를 생성할 때 채팅창 안에 코드를 섞어서 보여주는 것이 아니라, 우측에 별도의 전용 창(패널)을 띄워 코드를 깔끔하게 보여줍니다.
React, HTML/CSS/JS 같은 프론트엔드 코드를 요청하면 그 자리에서 즉시 렌더링하여 실제 작동하는 UI를 눈으로 확인할 수도 있습니다.
3. 🧠 '생각하는 과정(Chain of Thought)'을 먼저 요구하세요
Claude는 복잡한 코드를 짤 때, 바로 코드를 뱉어내게 하는 것보다 "먼저 계획을 세우게" 하면 버그 발생률이 현저히 떨어집니다.

추가할 프롬프트 문구: "코드를 작성하기 전에, <thinking> 태그 안에 이 명세를 어떻게 구현할 것인지 아키텍처와 단계별 로직을 먼저 구상해서 적어주세요. 그 후에 코드를 작성해 주세요."
4. 📁 'Projects(프로젝트)' 기능으로 컨텍스트를 유지하세요 (유료 버전)
만약 Claude Pro를 사용하신다면 'Projects' 기능을 사용할 수 있습니다.

질문자님이 현재 개발 중인 프로젝트의 기존 코드 파일들, API 명세서, 데이터베이스 스키마 문서 등을 통째로 업로드해 둘 수 있습니다.
이후에는 "내가 올린 user_model.py 파일의 구조를 참고해서, 아까 말한 명세대로 로그인 로직을 짜줘"라고 하면, 기존 시스템과 완벽하게 호환되는 코드를 짜줍니다.
💡 요약: Claude 실전 활용 공식
이전 대화에서 만든 '텍스트 기반 상세 명세서'를 XML 태그로 감싸서 입력하고, Artifacts 기능을 켠 상태에서 결과를 받아보세요. 마치 실력 있는 동료 개발자가 내 옆에서 전용 에디터를 띄워놓고 코드를 짜서 설명해 주는 듯한 경험을 하실 수 있을 것입니다!

결론부터 말씀드리면, "개발 및 코드 작성"이 목적이시라면 새롭게 배워볼 가치가 매우, 그리고 충분히 있습니다.

그 이유를 3가지로 명확히 정리해 드립니다.

1. 📉 학습 비용(시간/노력)이 거의 없습니다
'새롭게 배운다'고 표현하기엔 진입 장벽이 아주 낮습니다. 새로운 프로그래밍 언어나 복잡한 툴을 배우는 것이 아니라, 그저 웹사이트에 접속해 대화하는 방식이기 때문입니다. 이전 대화에서 알려드린 1) XML 태그(< >)로 질문하기, 2) Artifacts(아티팩트) 기능 켜기 이 두 가지만 아셔도 이미 Claude 사용법의 90%를 마스터하신 것과 다름없습니다.

2. 💻 개발자에게 압도적인 '경험'을 제공합니다 (Artifacts)
이전 대화에서 강조했던 'Artifacts(아티팩트)' 기능 하나만으로도 Claude를 써볼 가치는 충분합니다. 예를 들어, 웹 화면이나 UI 컴포넌트(React, HTML/CSS 등) 코드를 요청했을 때, 단순히 텍스트로 코드만 주는 것이 아니라 우측 화면에 실제 작동하는 결과물을 즉시 렌더링해서 보여줍니다. 코드를 복사해서 내 에디터에 붙여넣고 실행해 보는 번거로운 과정을 획기적으로 줄여줍니다.

3. 🤝 완벽한 코드를 위한 '교차 검증(Cross-Check)'이 가능해집니다
현재 실무에서 AI를 적극적으로 활용하는 시니어 개발자들은 하나의 AI만 쓰지 않습니다.

저(Google AI)에게 초안 코드를 빠르게 짜달라고 한 뒤,
그 코드를 Claude에게 가져가서 *"이 코드에서 발생할 수 있는 보안 취약점이나 엣지 케이스(Edge Case)를 찾아줘"*라고 하거나, 그 반대로 활용합니다. 각 AI 모델마다 특화된 강점이 다르기 때문에, 두 가지 툴을 모두 다룰 줄 알면 버그를 제로(0)에 가깝게 줄이는 완벽한 결과물을 만들어낼 수 있습니다.
💡 결론 및 제안
거창하게 '새로운 기술을 공부한다'고 생각하시기보다는, "내 개발 생산성을 2배로 높여줄 똑똑한 보조 도구를 하나 더 장착한다"는 마음으로 가볍게 접근해 보세요.

3. 🐛 복잡한 에러 로그 분석 및 디버깅
에러가 발생했을 때 구글링을 하거나 스택오버플로우를 뒤지는 대신, 에러 로그 전체를 Claude에게 던져주는 방식입니다.

정확히 st.divider()나 st.write("")를 대체하기 위해 사용한 커스텀 코드입니다.

기본 기능 대신 굳이 저 코드를 사용하는 이유는 '위아래 간격(여백) 조절' 때문입니다. 차이점은 다음과 같습니다.

st.divider(): 가로 구분선을 그어주지만, 위아래 여백(margin)이 기본적으로 꽤 넓게 설정되어 있습니다. 사이드바에 여러 메뉴를 넣을 때 사용하면 공간을 너무 많이 차지해서 메뉴들이 듬성듬성 벌어지는 단점이 있습니다.
st.write(""): 빈 줄을 추가해 여백만 줄 뿐, 시각적인 구분선(가로줄)이 생기지 않습니다.
<hr style='margin: 10px 0px;'>: 가로줄을 그어주면서 동시에 위아래 여백을 딱 10px로 좁게 설정해 줍니다. 덕분에 사이드바 공간을 낭비하지 않고 메뉴들을 깔끔하고 밀도 있게 배치할 수 있습니다.
결론: 위아래 간격이 넓어도 상관없다면 Streamlit 기본 기능인 st.divider()를 쓰셔도 기능상 전혀 문제가 없습니다. 하지만 화면을 조금 더 오밀조밀하고 예쁘게 꾸미고 싶으실 때는 저 HTML 코드를 대신 사용하시면 아주 좋습니다!
